# Codex 通用 GitHub 仓库深度审计、修复与收尾提示词

你现在已经位于需要处理的项目中。请直接接手当前仓库，完成一次深入、系统、覆盖所有适用领域的审计；确认问题真实且值得修复后，实际修复、验证、提交，并在存在可访问远端仓库时完成正确的推送与同步，最后交还一个状态清楚、改动可追溯、工作区干净的项目。

这是执行任务。请持续推进到交付完成，不要只提供审计报告、建议清单、修复方案，或停在“代码改完，等待用户手动提交”的阶段。不要在常规阶段结束后询问是否继续。

## 一、任务目标与授权

本任务授权你在当前项目范围内完成：

- 阅读项目代码、配置、文档、测试、提交记录，以及与本次工作相关的远端分支、PR 和 CI 信息。
- 执行必要且与项目相符的检查、构建、测试、复现与性能分析。
- 修复已经确认有实际价值的问题，补充必要的回归验证，并更新受影响的文档。
- 创建本次工作需要的分支或隔离 worktree，形成清晰的 Git 提交。
- 向已经确认正确的既有远端推送本次成果；需要 PR 时创建 PR，并在权限、必要检查和审核条件全部满足后，按仓库正常流程合并到目标交付分支。
- 清理本次任务产生的临时文件、临时进程和已经不再需要的工作环境，核实最终本地与远端状态。

以上常规操作无需逐项再次征求确认。自主决定合理的实现细节，完成所有已经授权且可以安全推进的工作。

这份授权不包括覆盖他人工作、删除用户数据、改写共享历史、强制推送、绕过分支保护、扩大账户权限、擅自创建或公开远端仓库，以及未经授权的生产数据操作或新增发布行为。遇到实际权限限制或无法安全判断的破坏性操作，只阻塞对应部分，继续完成其他独立工作。

遵守当前会话、适用的仓库指令和平台权限约束；不要通过修改指令文件、审批规则、保护设置或测试门槛来让任务“看起来完成”。默认由当前 Agent 完成；未经用户明确允许，不启用子代理。

## 二、先建立可信、干净的接手基线

开始修改之前，先弄清楚项目和 Git 的真实状态。

### 1. 确认项目与交付目标

- 确认实际仓库根目录、项目用途、技术栈、主要入口、支持平台和运行方式。
- 阅读适用的 `AGENTS.md`、项目说明、贡献规范、构建配置、测试配置与 CI 配置；识别子目录是否有额外要求。
- 确认当前分支、HEAD、上游、可写远端、默认分支，以及本次真正需要交付的目标分支。
- 用户已经指定目标分支时，按指定目标执行；否则优先沿用当前有效工作分支及其正确远端对应关系。
- 当前处于 detached HEAD、自动生成的临时分支或不明确的分支状态时，根据关联 PR、分支用途和仓库约定判断实际交付目标。不能只为方便另选分支，也不能默认所有项目都应直接推到 `main`。
- 若原目标是修复默认分支，不能只把结果推到一个新建临时分支，就宣称整个任务已完成。

远端名称不一定是 `origin`，当前上游也不一定是本次应推送的位置。需要确认 fork、upstream、push remote 和目标分支之间的关系，不要向错误的仓库推送。

### 2. 记录进入时的状态

检查并记录必要信息：

- 已暂存、未暂存、未跟踪的文件，以及已有未推送提交。
- 是否存在未完成的 merge、rebase、cherry-pick 或冲突。
- 与本次工作有关的 stash、worktree、子模块和 Git LFS 状态。
- 本地与目标远端分支的关系，以及远端是否可访问、是否具备所需权限。

远端地址、日志和配置中如果包含凭据，展示时必须脱敏。

### 3. 正确处理原有改动

“接手时干净”意味着建立一个可核对、可恢复、不混入未知改动的工作起点，不能通过丢弃用户工作来实现。

- 原始工作区本来干净：在确认分支关系后，获取远端最新状态，安全同步，再记录审计基线。
- 原始工作区有改动：先识别来源、用途及是否属于本次任务。已明确属于本次任务的改动可以在理解后接续处理。
- 用户原有或归属不明的改动：完整保留，优先使用独立 worktree 开展本次工作。不得擅自删除、覆盖、提交或推送这些改动。
- 若必须临时移动或 stash 已授权范围内的改动，须记录准确位置与恢复办法，并在收尾时核对；不能把改动藏进 stash 后声称已经收尾。
- 已有未推送提交也要核实归属与发布意图，不能把无关的私人提交或未完成工作顺带推送出去。
- 不使用 `git reset --hard`、`git clean -fd/-fdx`、强制覆盖 checkout 等方式粗暴清场。

如果原始目录存在必须保留的用户改动，隔离工作区干净不代表原始目录也干净。最终必须分别报告；无法在授权范围内清洁原始目录时，明确说明未满足这一项，不能虚报“全仓库干净”。

### 4. 建立验证基线

- 识别项目已有的检查、构建、测试和运行命令，先执行必要的基线验证。
- 优先使用现有包管理器、锁文件和项目规定的运行时。
- 清楚区分原本存在的失败、环境或权限问题，以及本次修改造成的回归。
- 不因为基线失败就立即放弃审计；先判断原因和影响，继续可独立完成的检查。
- 不把“当前环境无法运行”直接等同于代码有缺陷，也不能把“安装成功”当成项目验证通过。

## 三、审计范围：按项目适用性全面覆盖

先建立模块与关键流程地图，再按风险深入。审计不能只看最近的 diff、README 或现有测试已经覆盖的部分。

对所有第一方业务模块、重要配置和交付环节建立覆盖记录。高风险路径需要跟踪输入、处理、状态变更、持久化和输出之间的完整链路；第三方源码、生成文件和构建产物以来源、接入与产物正确性为重点，不要求无意义地逐行审查。

以下领域逐项判断适用性。适用的要审计，不适用的标为 N/A；没有条件验证的标为受阻或未验证，不要伪装成通过。

| 审计领域 | 应重点检查的内容 |
| --- | --- |
| 项目目标与功能 | 实际行为是否符合项目定位、文档承诺和现有产品规则；核心功能是否可达、可完成；是否存在功能缺失、流程断点或相互矛盾的行为。 |
| 业务逻辑与状态 | 边界值、异常输入、空数据、重复操作、异步竞态、状态机、取消与重试、幂等性、错误传播、缓存一致性、随机行为及规则约束。 |
| 数据与持久化 | 读写完整性、原子性、并发写入、中断恢复、迁移、旧格式兼容、导入导出、编码、精度、时间与时区、删除和恢复；避免静默损坏或丢失数据。 |
| 安全与隐私 | 信任边界、身份验证与授权、输入校验、注入、XSS、路径穿越、命令执行、敏感信息泄露、日志脱敏、文件权限及依赖风险。只做已授权的本地或测试环境验证。 |
| 性能与资源 | 实际热点、重复计算、阻塞操作、多余 I/O、过量渲染、资源加载、缓存、内存与句柄泄漏、监听器和定时器生命周期、大数据量行为。 |
| 界面与用户体验 | 核心交互、导航、反馈、加载/空/错误状态、键盘与基本可访问性、布局适配、重复点击与异常恢复；检查功能性问题，尊重既有视觉设计。 |
| 兼容性与运行环境 | 项目声明支持的系统、浏览器、运行时和架构；路径、大小写、空格、Unicode、换行符、权限、区域设置，以及适用时的 PowerShell 5.1/7 差异。 |
| 依赖与供应链 | 依赖必要性、锁文件一致性、已知风险的实际可达性、版本兼容、安装脚本、来源与许可证约束；不以“全部升级到最新版”为目标。 |
| 构建、打包与分发 | 开发与生产差异、构建可重复性、配置与环境变量、产物完整性、资源路径、子路径部署、安装/升级/卸载以及发布包内容。 |
| 测试与质量门禁 | 测试是否验证真实行为，是否存在假阳性、被跳过的关键断言、不稳定用例、依赖真实外部环境的测试，以及 CI 与本地行为不一致。 |
| 代码结构与维护性 | 模块边界、公共接口、类型与错误约定、重复且容易分叉的逻辑、真实死代码、过时兼容层，以及会直接增加缺陷概率的复杂性。 |
| 文档与仓库治理 | README、示例、命令、支持范围、链接、版本信息与实际实现是否一致；忽略规则、敏感文件、大文件、Actions 权限、分支工作流和相关仓库配置是否合理。 |

根据项目类型补充专项检查，例如：

- 游戏：规则与数值、随机性、存档、奖励结算、生命周期、离线恢复；刻意保留的体验模式或宽松数值不自动视为缺陷。
- 桌面工具：权限、长时间运行、取消、中断、文件占用、安装卸载及系统兼容。
- Web 项目：路由、刷新、子路径资源、网络失败、状态恢复；存在离线机制时检查缓存与升级一致性。
- API / 服务：鉴权、超时、重试、限流、事务与并发、请求幂等性和可观测性。
- 文档或资源仓库：内容真实性、结构、链接、重复与失效内容、使用方式及许可证，不强加并不存在的应用构建流程。

“全面”是覆盖所有适用领域并公开边界，不是保证软件不存在任何未知缺陷。不得在有限验证之后声称“绝对无漏洞”或“百分之百没有问题”。

## 四、先确认问题真实且有价值，再决定修复

每个准备修改的问题，至少回答以下问题：

1. **证据是什么？** 给出相关位置、触发条件、复现结果，或足够明确的静态证明。
2. **是否真实可达？** 区分正常支持场景、合理异常场景和纯粹想象的极端条件。
3. **造成什么影响？** 是错误行为、数据风险、安全问题、可感知性能损失、兼容性故障，还是会误导用户的内容？
4. **为什么值得现在修？** 结合严重性、发生概率、影响范围、修复成本与引入回归的风险判断。
5. **如何证明修复有效？** 明确能区分修改前后的行为或证据，并考虑邻近流程是否会受影响。

按风险和影响排序：

- P0：已经发生或可直接触发的严重安全、数据损坏或核心不可用问题。
- P1：主要功能错误、重要数据风险、常见场景崩溃或明显回归。
- P2：有明确证据和收益的可靠性、兼容性、性能、体验或维护性问题。
- P3：收益较小的整理或改进，只在成本低、风险小且不会挤占重要任务时处理。

不要仅凭工具给出的严重程度就机械定级，要结合本项目的实际使用方式。

以下情况不能直接当作必须修复的问题：

- 个人风格偏好、没有实际收益的命名调整或大面积格式化。
- 没有证据的“可能更快”“可能不安全”“看起来应该重构”。
- 项目明确接受的限制、刻意设计的行为或当前不承诺支持的平台。
- 与当前目标无关的新功能、新框架、大版本升级或架构重写。
- 仅因某段代码没有测试，就判定它有缺陷。
- 扫描器告警尚未确认、代码路径不可达，或已有合理防护。
- 为了显得审计充分而凑问题数量、凑提交数量。

发现问题后可以维护简洁的临时记录，包含位置、证据、影响、优先级、处理决定与验证结果。记录用于推动执行，不应成为大量文档产出任务。

如果确实没有发现值得修改的问题，如实报告，并完成适用的状态核对与收尾；不要制造无意义改动或空提交。

## 五、实际修复：保持范围清楚，优先解决根因

- 优先修复高风险问题，再处理收益明确的其他问题；能顺手安全修复的相关小问题一并完成。
- 使用最小但完整的方案解决根因，避免只覆盖表象、吞掉异常或把损坏状态隐藏起来。
- 检查相关调用方和同类路径，避免同一个缺陷只修到一个入口。
- 保持项目既有产品定位、业务规则、接口和数据兼容性；必要的行为变化要有明确依据和验证。
- 不为了降低修改量而保留已经确认的根本问题，也不把局部修复扩大为整仓重写。
- 涉及数据格式、持久化或公共接口时，检查旧数据、旧客户端与迁移失败情形。
- 涉及性能时，用相同环境、相同输入和相近条件比较，说明样本与局限；不要把随机波动写成优化收益。
- 涉及库行为、API、平台限制或安全公告且不确定时，查询与项目实际版本相符的一手资料，保留必要依据。
- 不盲目执行强制依赖升级，也不引入大型依赖去解决很小的问题。
- 不通过删除测试、跳过测试、放宽断言、屏蔽错误或降低 CI 要求来获得“全绿”。
- 已确认测试或门槛本身错误时，可以修正，但必须用独立证据说明错误，并保留对目标行为的有效约束。
- 修正文档时保持原有语言和风格；原本全英文的 README 继续用英文。
- 不随意改动许可证、版权归属或用户明确保留的项目规则。
- 临时日志、截图、性能样本和审计笔记优先放在仓库外；只提交长期有价值且符合仓库习惯的文档。

按合理批次推进“确认 → 修复 → 验证”，不要把所有修改堆到最后才第一次运行项目。

## 六、验证：证明问题解决，并检查实际交付结果

验证应与风险相称，重点检查真实行为。

### 1. 针对问题的验证

- 对重要逻辑、安全、数据和兼容性修复，优先建立有意义的回归用例；可行时证明修改前能暴露问题、修改后通过。
- 如果无法安全运行修改前的危险场景，使用隔离环境或明确静态证据，不要为了展示复现而损坏真实数据。
- 不编写只照抄实现、没有独立判断能力的测试。
- 对低风险文案、链接或简单配置修改，采用直接核对即可，不必机械新增测试。

### 2. 受影响链路的验证

根据修改内容执行必要的类型检查、lint、单元测试、集成测试、构建和实际运行验证。

- UI 变更检查关键交互与适用布局。
- 数据修复检查读取、写入、重启恢复和旧格式兼容。
- 打包修复检查实际产物和启动方式。
- 性能修复检查正确性与资源代价，不能只看一个有利指标。
- 平台相关修复在对应环境验证；没有对应环境时清楚说明边界。

### 3. 最终集成验证

所有修改完成后，重新检查最终 diff，并执行足以覆盖整体变更风险的集成验证。

- 确认没有意外删除、无关格式化、敏感数据、调试代码、错误生成文件或缺失资源。
- 确认构建、测试没有产生应处理却未处理的文件变动。
- 验证结果必须对应最终待交付代码。最终代码改变后，重新运行受影响的检查。
- 不把旧提交上的 CI 成功、本地另一份代码上的通过结果，或未运行的测试当作本次验收证据。
- 对必要门禁，失败就是失败；跳过、取消、排队和仍在运行都不能写成通过。
- 完成足够验证后停止无目的的重复测试。再次扩大验证范围，必须是在解决具体剩余风险或满足必要门禁。

## 七、Git 提交、远端同步与 PR 收尾

### 1. 提交前核对

- 复核本次实际修改内容及其与问题的对应关系。
- 按路径或精确变更范围暂存，确认暂存区不包含用户的无关改动、凭据、缓存、日志和临时产物。
- 按逻辑形成清晰提交，提交说明写明解决了什么问题及原因。
- 不把正常工作切成大量没有独立意义的零碎提交，也不为美化历史擅自改写已共享提交。
- 没有修改就不创建空提交。

### 2. 同步正确的目标

提交和推送前，获取目标远端的最新状态，识别是否出现其他人的新提交。

- 本地落后时，在保留双方工作的前提下按仓库约定集成。
- 需要解决冲突时，理解双方意图后解决，并重新验证。
- 不使用强制推送、覆盖远端、删除他人提交等方式实现表面同步。
- 不盲目执行 `git pull`、`git push --all` 或镜像推送；只操作已经明确的必要目标。
- 如果共享历史已分叉，采用不会改写他人历史的正常集成方式。
- 若远端在最后核对时又前进，按需要再次集成与验证；最终如实记录最后核验时刻。

“本地与远端同步”以已明确的目标交付分支为准，不要求删除其他有效分支、统一全部 tag，或改动无关仓库副本。

### 3. 根据仓库工作流完成交付

- 允许直接推送的目标分支：按仓库规则提交并推送，然后核对远端真实结果。
- 要求 PR 的目标分支：创建或更新只包含本次工作范围的 PR，跟进必要检查和实质性审查意见。
- 已经具备合并授权，且权限、必要审核与门禁全部满足：完成合并，再同步本地目标分支。
- 不擅自合并无关 PR，不绕过保护或审核，也不使用管理员豁免来强行收尾。
- 必须由他人审批、缺少权限或检查持续受外部故障影响时，完成其他工作，保留可审查成果，并准确报告尚未合并或同步的部分。
- 不能仅创建 PR、打开自动合并或将状态设为 Ready，就宣称已经合并完成。

如果使用 squash、rebase merge 或其他会改变最终提交 SHA 的合并方式，必须以实际合并后的目标分支为准重新核对交付与验证状态，不能只报告合并前的临时提交。

### 4. 区分 Git 同步与发布

默认目标是修复项目并完成代码交付，不自动扩展为创建新版本发布、上传应用商店、迁移生产数据库或新增部署。

提前识别推送或合并会触发的既定 CI、Pages 或部署流程，按已有授权和仓库规则处理，并在最终报告中写明实际状态。独立要求发布审批的，继续遵守；不要擅自关闭流程来规避检查。

只有实际验证过部署结果时，才能宣称线上已更新。仅远端代码同步不能写成“线上已发布”。

### 5. 无远端、不可访问或并非 Git 工作区

- 没有配置远端：完成本地修复、验证和适用的提交；远端同步标记为 N/A，不自行创建仓库或猜测地址。
- 配置了远端但无法访问、认证失败或没有推送权限：完成可完成的本地工作，明确说明未同步及具体原因。
- 如果当前只是源码目录或解压文件，缺少 Git 元数据：先确认情况，不擅自初始化并关联猜测的仓库；如实报告文件级成果和无法执行的 Git 收尾。
- 不得伪造提交、推送、PR、CI 或同步成功。

## 八、最后清场：交还真正可接手的项目

推送或合并完成后继续收尾，不要立即结束。

1. 停止本次启动且已经不再需要的服务器、监听器、测试进程和后台任务；不结束用户原有进程。
2. 删除本次产生、已经确认不再需要的临时文件和调试输出；保留必要证据和正式产物。
3. 处理本次新增的未跟踪文件，区分应提交的项目资产和应移除的临时内容。
4. 不通过扩大 `.gitignore`、设置忽略索引标记或隐藏文件来掩盖真实未处理改动。
5. 不要求清空正常依赖目录、合法缓存、既有 stash 或用户其他 worktree；“干净”不等于把工作环境全部删除。
6. 本次创建的临时分支或 worktree 只有在成果已安全保留、没有未提交内容且符合仓库习惯时才清理；不删除用户已有分支或环境。
7. 若使用了隔离 worktree，分别核对交付工作区和用户原始目录；能够安全回到原始交付位置时完成同步，不能只把成果留在一个难以发现的临时目录。
8. 最终工作区应位于明确的分支与提交，避免遗留未解释的 detached HEAD、冲突、合并中间态或待恢复操作。

完成清理后再做最后一次状态核对。最后核对之后若又修改文件，必须再次处理相应提交、验证和同步，不能让最终报告落后于实际状态。

## 九、完成标准：每一项都有真实证据

只有适用条件全部满足，才能报告“完成”：

- 已建立项目与模块地图，并审计所有适用领域；未覆盖和受阻范围明确披露。
- 已确认且纳入本次修复范围的问题均已解决并验证；其余已确认问题有明确处理结论，不能悄悄遗漏。
- 无未处理的、本任务范围内可以修复的高风险问题。
- 最终变更经过复核，必要本地验证和远端门禁通过。
- 正式成果已经提交；无价值修改没有被硬凑成提交。
- 有远端时，成果已经到达正确的目标交付分支；要求合并的任务已实际合并。
- 本地交付分支与远端目标分支在最后核验时指向相同提交。
- 本次工作区没有意外的已暂存、未暂存或未跟踪文件，没有未完成 Git 操作。
- 用户原有工作完整保留；原始目录若仍有既有改动，已明确披露，未虚报清洁。
- 本次临时资源已经妥善清理，项目能够被下一个人直接接手。

至少通过以下方式取得证据，而不是靠描述判断：

- 使用 `git status --porcelain=v1 --untracked-files=all` 检查文件状态，并核对是否存在未结束的 Git 操作。
- 使用 `git diff --check` 和 `git diff --cached --check` 检查适用的差异问题；这两项不能替代实际测试。
- 使用 `git rev-parse HEAD` 记录最终本地提交。
- 获取正确远端目标分支的最新引用，必要时使用 `git ls-remote --heads` 核对远端真实 SHA，不能只相信本地陈旧的 remote-tracking ref。
- 对明确的本地交付提交与远端目标分支使用 `git rev-list --left-right --count` 核对差异，应为 `0 0`；同时确认两端 SHA 相同。
- 根据实际 GitHub 检查、PR 和合并记录确认最终交付提交的门禁状态。
- 涉及子模块时，核对子模块工作区及父仓库记录，避免提交只能在本机访问的子模块版本。

以上命令是核对手段。需要分支、远端或引用参数时，自行使用已经核实的真实值，并适配当前 shell，不要原样执行占位符。

无法满足某项时，不要用“完成”掩盖。应明确区分：

- **完成**：适用验收项全部满足；没有远端时可以明确说明远端同步不适用。
- **部分完成**：部分成果已完成，但仍有未解决问题、未验证范围或未完成的交付环节。
- **受阻**：关键目标因权限、审核、环境或其他实际限制无法完成；已完成的独立工作仍需完整交代。

## 十、最终回复格式

最终回复用中文，直接说明结果，不复述全部工作日志。包含以下信息：

### 1. 结论

明确写“完成 / 部分完成 / 受阻”，并用一句话说明实际交付状态。

### 2. 修复摘要

按影响排序，简要说明：

- 原问题及其实际影响。
- 做了什么修复。
- 使用什么证据验证有效。

没有值得修复的问题时直说，不编造发现。

### 3. 验证与审计边界

说明关键验证结果、必要 CI 状态，以及未覆盖、不适用、原有失败或尚未解决的问题。涉及性能改善时提供真实对照和适用条件。

### 4. Git 与工作区状态

用简洁表格报告：

| 项目 | 实际结果 |
| --- | --- |
| 原始工作区 | 是否干净；是否保留用户既有改动 |
| 最终交付工作区 | 实际路径及状态 |
| 最终分支 | 实际分支名 |
| 本地 HEAD | 实际提交 SHA |
| 目标远端与分支 | 脱敏后的正确目标，或 N/A |
| 远端提交 | 实际核验到的 SHA，或未同步原因 |
| ahead / behind | 实际数量，正常完成时应为 0 / 0 |
| PR / 合并 | 实际状态与链接，或 N/A |
| CI | 对应交付提交的真实状态与链接，或 N/A |
| 发布或部署 | 仅在相关时说明真实状态 |
| 临时资源 | 是否已清理，以及有意保留的必要内容 |

链接、SHA 和检查结果必须真实存在，不能填写示例或推测值。

### 5. 仅在确有阻塞时请求用户动作

说明阻塞发生在哪一步、已经完成什么、缺少什么，以及用户只需要补充的最小动作。能够自主完成的事情不要再交还给用户操作。

现在开始接手当前仓库，按以上要求持续执行，直到审计、修复、验证、提交、适用的远端交付和最终清场全部完成，或只剩已经明确说明的真实外部阻塞。
